# 새 프로젝트 구조 설계 v1 (제안)

작성 2026-11-13. 상태: **제안**이에요. 사용자가 정한 것과 제가 제안하는 것을 나눠 적었어요.

## 사용자가 정한 것 (2026-11-13 대화)
1. 기존 저장소(`chatbotgmm/server`)에 덧붙이지 않고 **새 저장소**(`chatbotgmm/prototype`)에서 깨끗하게 다시 만든다. 이유: 코드가 겹치고, 예전 프로젝트가 같이 올라가 용량이 커졌다. 기존 저장소의 `.git`은 1.7GB로 확인했다.
2. 기준은 **GMM110 방범대 네이티브 앱**이다(`docs/GMM110-FEATURES.md`).
3. **웹으로 먼저** 기능을 모두 다시 만들어 빠르게 고치고, 시제품이 완성되면 **Godot**으로 옮겨 다듬고 출시한다. 웹과 앱(Godot) 둘 다 낸다.
4. **서버도 새로** 깨끗하게 만든다.
5. 첫 커밋은 `main`에 올린다.

## 원칙 (제안)
1. **규칙은 한 곳에만.** 전투·성장·조합·모집 계산은 `shared/`의 순수 TypeScript 함수로만 둔다. 화면·DB·네트워크에 의존하지 않는다. GMM110에서 같은 계산이 서버·앱 여러 곳에 흩어졌던 문제를 막으려는 거예요.
2. **서버가 판정, 화면은 표시.** 승패·보상·확률은 서버만 정한다. 웹과 Godot은 같은 HTTP API를 부르는 화면일 뿐이다. 그래서 Godot으로 옮길 때 **화면만** 새로 만들면 된다.
3. **수치는 데이터 파일로.** 60종·기술·조합식·스토리·정책 수치는 `data/*.json`에 둔다. 시험값과 승인값을 파일 안에 표시한다(GMM110의 `productionBalanceApproved` 방식 유지).
4. **예전 체계는 가져오지 않는다.** 수비대 전투, 145종 챗봇, 예전 대전은 옮기지 않는다(「정해야 할 것」 1번에서 확인).
5. **저장소를 가볍게.** zip·apk·원본 작업 파일·중복 그림은 올리지 않는다. 그림은 쓰는 것만, 압축(webp)해서 올린다.

## 폴더 구조 (제안)
```
prototype/
├─ shared/        규칙 엔진(순수 TS): 전투 계산, 성장 곡선, 환생, 조합 판정, 모집 확률, 데이터 검사
├─ server/        HTTP API + DB. shared를 불러 판정하고 저장
├─ web/           웹 화면(시제품). API만 부름
├─ data/          60종 카탈로그, 기술, 조합식, 스토리, 정책(시험값/승인 표시)
├─ assets/        실제로 쓰는 그림·소리만(압축본)
├─ tools/         데이터 검사, 시험 서버, 화면 캡처 검토
├─ docs/          설계·기능 목록·API 명세
└─ godot/         (나중) Godot 프로젝트. 같은 API, 같은 data
```

## 기술 선택 (제안, 바꿀 수 있음)
| 부분 | 제안 | 이유 |
|---|---|---|
| 언어 | TypeScript (Node 22) | GMM110 서버·규칙이 TS라 계산식을 검증하며 옮기기 쉬움 |
| 서버 | Fastify | GMM110에서 쓰던 것과 같아 익숙함 |
| DB | SQLite + Prisma로 시작 | 서버 한 대 운영에 충분함. 필요하면 나중에 바꿈 |
| 웹 화면 | TS + DOM/CSS, Canvas는 전투 연출에만 / 묶기는 esbuild | 빠르게 고치기 쉽고 의존성이 적음. Godot의 Control 노드 배치와 사고방식이 비슷함 |
| 시험 | Vitest(규칙·API), Playwright(화면 캡처) | 계산식은 숫자로, 화면은 캡처로 확인 |

## Godot으로 옮길 때를 위한 약속
- 웹 화면 구조를 Godot 장면처럼 짠다. 화면 하나 = 장면(scene) 하나이고, API·계정 상태는 전역 모듈 하나(Godot의 autoload에 해당)가 맡는다.
- 화면끼리 직접 부르지 않고, 「장면 전환(이름, 인자)」과 「신호(signal)」로만 연결한다.
- 화면 크기는 가로 전용. 기준은 휴대폰 915×412와 큰 화면 1280×720(GMM110 검토 기준과 같음).
- API 응답은 화면에 바로 쓸 수 있는 모양으로 준다(남은 턴, 이유 문구, 사용 가능 여부). 그래서 Godot 쪽에서 규칙을 다시 계산하지 않는다.
- `docs/API.md`(2단계에서 작성)를 웹·Godot 공통 계약으로 쓴다.

## API 방향 (초안)
- 주소: `/api/v1/...`, JSON.
- 모든 쓰기 요청은 `requestId`(같은 요청을 다시 보내도 한 번만 처리)와 필요한 경우 `revision`(낡은 화면 명령 거절)을 가진다. GMM110에서 검증된 방식이에요.
- 로그인: 6자리 코드, 카카오. 세션은 웹은 쿠키, 앱은 머리글 토큰.
- 묶음(GMM110 기능 기준): 계정 · 마을(home) · 보유 개체 · 도감 · 첫 갈매미 · 모집 · 조합 · 편성 · 전투 · 스토리/의뢰 · 모험 · 일반전/랭크전 · 환생 · 방범대장 · 상점/우편/일일.

## 정한 것 (사용자 결정, 2026-11-13)
1. **예전 체계는 뺀다**: 수비대 전투, 145종 카톡 챗봇, 예전 실시간 대전은 새 프로젝트에 옮기지 않는다.
2. **시제품 동안은 시험 계정만** 쓴다. 운영 계정·DB는 이어받지 않는다.
3. **시험값도 그대로 옮긴다.** 시험값 표시는 유지한다.
4. **그림은 60종과 GMM110에서 실제로 쓰인 것만** 옮긴다.
5. **기존 도메인(gmm.dpdns.org) 아래**에 띄운다. 경로와 배포 방법은 서버 단계에서 정한다.
6. **60종 전투 증강체는 나중에 넣는다**(2026-11-13). GMM110 이후 운영 서버(GMM111, `chatbotgmm/server`의 `server-snapshot/gmm111-20261103`)에 `roster60-current-augment-*`로 추가된 것이 있어요. 넣을 때는 그 코드를 원본으로 삼아, 지금처럼 원본을 실제로 돌려 만든 기준 결과와 비교하며 옮겨요.

## 비교 시험의 한계 (3단계 기록)
- 시험이 실제 차이를 잡는지 일부러 계산을 틀리게 넣어 확인했어요. 공개 시점·경험치 반올림·저항 배율·강제 교체 순서는 잡혔어요.
- 「전투 중 관측을 종 단위 지식에도 더하는 부분」(`addDefenseObservation`의 base 갱신)은 꺼도 시험이 통과했어요. 원본에서 전투 안의 공개 정보는 이번 전투 관측이 종 단위 지식을 덮어쓰기 때문에(`{...base,...local}`), 상대가 한 마리인 PvE에서는 결과에 영향이 없어요. 대전(PvP)을 옮길 때 다시 확인해요.
- 기준 결과에 없는 상황: 100턴 무승부, 모험 도망 실패(도망 판정 함수 자체는 따로 비교함), 상한 초과로 경험치가 잘리는 정산(지급 함수 자체는 따로 비교함).

## 4단계 기록
- 화면은 GMM110과 비슷하게(사용자 결정): 첫 화면(`TitleView`), 마을(`village-loop-v2/manifest.json` 배치 그대로), 전투(ui-v3 나인패치·아이콘, `NavyWorkbenchTheme` 색).
- 전투연습장의 「일반전」은 원본에서 사람 대전(30초 뒤 AI)이에요. 대전은 7단계라 지금은 **AI 연습 상대(PvE 훈련 조우)**로 연결했고, 화면에 「지금은 AI 연습 상대」라고 밝혔어요. 「랭크전」과 다른 건물 메뉴는 「다음 단계」로 표시해요. → 7-2단계에서 실제 대전으로 바꿨어요.
- 석상은 스토리 연결 전이라 1단계 그림으로 고정했어요.
- 마을 건물 이름판은 글자 그림(nameplates.png) 대신 실제 글자로 그려요.

## 5단계 기록
- 계산(`shared/src/acquisition.ts`)은 원본을 실제로 돌린 기록(`shared/test/fixtures/gmm110-acquisition.json`)과 비교해요: 지급 레벨 60종, 모집 23판(굴림 값을 같게 넣어 후보·새로고침 비교, 등급 경계 굴림 포함), 기술 계승 250건, 조합 40판(미리보기 지문까지 같은 값), 보유 상세.
- 원본과 다르게 한 것:
  - 「커먼 선택지급권」은 원본에서 우편으로 와요. 우편함은 8단계라 지금은 마을 안내 칸에서 바로 받아요.
  - 일일 미션 집계(모집·조합 횟수)는 8단계에서 연결해요.
  - 원본의 예전 「바로 뽑기」(`recruit`)는 옮기지 않고, 지금 앱이 쓰는 후보 방식(`recruit/session`)만 옮겼어요.
  - 조합 재료는 지금 레벨 높은 개체부터 자동으로 골라요. 원본 화면처럼 직접 고르기는 다듬기 단계에서 해요.
- 새 시험 계정은 빈 계정(지원서 30장, 원본 DB 기본값)으로 시작해서 원본 흐름(갈매미맨 → 튜토리얼 → 커먼 고르기)을 따라가요.

## 6단계 기록
- 계산(`shared/src/story.ts`)은 원본을 실제로 돌린 기록(`shared/test/fixtures/gmm110-story.json`, 생성기 `tools/parity/generate-story.ts`)과 비교해요.
  - 원본 스토리 서비스로 강한·보통·약한 파티 5개가 의뢰를 진행한 요청 순서를 그대로 다시 밟으며, 매 단계 화면 상태·오류 코드·전투 상대(흑화·악당)·경험치 계획·경험치·귀환 보상·흑화 재료를 비교해요.
  - 보통 진행에서는 드러나지 않는 경계(흑화 재료 누적 조건 경계값, 석상 단계가 낮아지지 않음, 조각 덮어쓰기, 부화)는 시작 상태를 직접 만들어 비교해요.
  - 콘텐츠 검사 17가지, 악당 개체 49건, 모험 기본 경험치 120건, 일반 모험 8판.
  - 일부러 틀리게 넣어 본 계산(체력 배율 내림, 흑화 재료 누적 조건 무시·경계 `>`, 스토리 모험 대기 50%, 악당 흑화 재료, 이어 보기 위치, 귀환 전 READY, 석상 단계 덮어쓰기, 조각 더하기, 부화 빠짐, 조우 순서, 악당 기술 레벨)은 모두 잡혔어요.
- 원본에서 경험치 조절 정책(두 번 이기면 한 레벨)이 있으면 스토리 전투도 그 계산을 쓰고, 스토리 경험치 정책(`story-unit-xp-policy.json`)은 원래 보상 값으로만 쓰여요(`roster60-battle.ts`의 계획 만들기와 정산 순서로 확인). 그래서 원본의 스토리 경험치 맡김(escrow) 경로는 옮기지 않았어요.
- 원본과 다르게 한 것:
  - 출항: 원본은 출발 예약 → 모험 시작 → 연결 → 전투 만들기를 여러 거래로 나눠 끊겨도 이어 가게 했어요. 새 서버는 DB 한 대·플레이어별 직렬 처리라 거래 하나로 처리해요. 그래서 `pendingDeparture`는 늘 `null`이고 스토리 revision이 오르는 횟수가 원본과 달라요(비교 시험에서 revision은 빼고 비교).
  - 재료 모험과 의뢰 모험은 모험 기록에 표시(`material`, `storyQuestId`)를 남기고, 다른 종류의 모험을 이어 쓰려 하면 거절해요(원본보다 엄격).
  - 방범대장 경험치(의뢰 완료·모험 귀환)는 7단계, 일일 미션(모험 귀환) 집계는 8단계에서 연결해요. 모험 귀환 승리 기록은 지금부터 남겨요.
  - 원본의 6마리 예전 모험 예외는 옮기지 않았어요(새 시험 계정만 쓰므로).
- 화면: 원본처럼 마을 위에 이야기 창을 띄워요(석상 = 메인 이야기, 주민 = 부탁, 기록소 「이야기 기록」, 선착장 「탐험」「스토리 외부 출항」). 석상 그림은 서버의 석상 단계(1~5)를 따라요.
- 그림: 흑화 8종은 원본 PNG를 해시 대조 후 webp로 줄여 넣었어요. 악당 5명은 원본도 기존 종 앞모습을 임시로 써서 새 그림이 없어요.
- 비교 시험의 한계: 전투 한 판의 진행(턴 계산)은 2단계 비교 시험이 맡고, 6단계 비교는 원본 전투가 끝난 상태를 입력으로 써요. 스토리 전투에서 지는 경우(악당에게 패배)와 흑화 재료 상한(20억)은 기록에 없어요.

## 7-1단계 기록(방범대장·환생)
- 7단계는 둘로 나눠요: 7-1 방범대장·환생, 7-2 일반전·랭크전(사람 매칭·30초 뒤 AI·랭크 점수).

## 7-2단계 기록(일반전·랭크전)
- 원본에서 60종 대전은 `src/roster60-pvp.ts`예요. `src/pvp/*`는 예전 실시간 대전(수비대·증강체)이라 옮기지 않았어요(정한 것 1번).
- 계산(`shared/src/pvp.ts`): 접속 판정, 랭크 점수(LP·승급전·강등·MMR), 일반전 점수, 일반전 경험치(v2), 랭크 자격·환생 이력 묶음, 매칭, 턴 처리, AI 행동, 시간 초과, 연출 기록, 패배 안내.
- 비교 방법: 원본 `RosterPvp`를 가짜 시계로 실제로 돌리고(사람끼리·30초 뒤 AI·거절·수락 시간 초과·접속 끊김·입력 시간 초과·랭크 여러 판·점수 차/등급 차 대기), 원본 내부 메서드(턴 처리·AI 선택·매칭·종료)를 감싸 입력·출력을 기록했어요(`tools/parity/generate-pvp.ts`, `shared/test/fixtures/gmm110-pvp.json`).
  새 함수에 같은 입력을 넣어 같은 출력이 나오는지 봐요: 턴 처리 379번, AI 선택 176번, 매칭 178번, 종료 21번(경험치·방범대장·점수), 접속 판정 30줄, 랭크 점수 200판, 패배 안내.
  - 기록에서 뺀 것: 사건마다 붙는 공개 정보 전후값(intel). 그 계산(observedOpponentIntel)은 2단계 비교 시험이 맡아요.
- 일부러 틀린 계산 15가지 중 14가지가 잡혔어요. 못 잡은 1가지는 「행동 전에 쓰러져 아이템을 돌려받음」인데, 원본에서도 교체·아이템이 먼저 처리돼서 턴 안에서는 일어날 수 없는 경로예요. 실제 환불(끝날 때 고른 아이템 돌려주기)은 서버 시험에서 확인해요.
- 서버 시험(`server/test/pvp.test.ts`, 가짜 시계): 사람끼리 끝까지, 30초 뒤 AI, 거절 후 같은 순서로 다시 대기, 항복 때 고른 아이템 환불, 90초 접속 끊김의 증명된 승리(방범대장 150), 입력 시간 초과, 랭크(Lv30으로 맞춤·LP +20·AI 없음), 랭크 자격, 대전 대기 중 환생 막기.
- 원본과 다르게 한 것:
  - 모든 대전 쓰기를 서버 하나의 직렬 처리로 해요(원본은 DB 잠금 행).
  - 일반전 경험치 장부·아이템 예약 표 대신 방 상태로 한 번만 처리해요(방이 FINISHED로 바뀌는 쓰기 안에서 지급, 고른 아이템은 방 상태에 적고 개수에서 1 빼 둠).
