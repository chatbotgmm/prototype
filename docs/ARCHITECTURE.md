# 새 프로젝트 구조 설계 v1 (제안)

작성 2026-11-13. 상태: **제안**이에요. 사용자가 정한 것과 제가 제안하는 것을 나눠 적었어요.

## 사용자가 정한 것 (2026-11-13 대화)
1. 기존 저장소(`chatbotgmm/server`)에 덧붙이지 않고 **새 저장소**(`chatbotgmm/prototype`)에서 깨끗하게 다시 만든다. 이유: 코드가 겹치고, 예전 프로젝트가 같이 올라가 용량이 커졌다. 기존 저장소의 `.git`은 1.7GB로 확인했다.
2. 기준은 **GMM110 방범대 네이티브 앱**이다(`docs/GMM110-FEATURES.md`).
3. **웹으로 먼저** 기능을 모두 다시 만들어 빠르게 고치고, 시제품이 완성되면 **Godot**으로 옮겨 다듬고 출시한다. 웹과 앱(Godot) 둘 다 낸다.
4. **서버도 새로** 깨끗하게 만든다.
5. 첫 커밋은 `main`에 올린다.

## 원칙 (제안)
1. **규칙은 한 곳에만.** 전투·성장·조합·모집 계산은 `shared/`의 순수 TypeScript 함수로만 둔다. 화면·DB·네트워크에 의존하지 않는다. GMM110에서 같은 계산이 서버·앱 여러 곳에 흩어졌던 문제를 막으려는 거예요.
2. **서버가 판정, 화면은 표시.** 승패·보상·확률은 서버만 정한다. 웹과 Godot은 같은 HTTP API를 부르는 화면일 뿐이다. 그래서 Godot으로 옮길 때 **화면만** 새로 만들면 된다.
3. **수치는 데이터 파일로.** 60종·기술·조합식·스토리·정책 수치는 `data/*.json`에 둔다. 시험값과 승인값을 파일 안에 표시한다(GMM110의 `productionBalanceApproved` 방식 유지).
4. **예전 체계는 가져오지 않는다.** 수비대 전투, 145종 챗봇, 예전 대전은 옮기지 않는다(「정해야 할 것」 1번에서 확인).
5. **저장소를 가볍게.** zip·apk·원본 작업 파일·중복 그림은 올리지 않는다. 그림은 쓰는 것만, 압축(webp)해서 올린다.

## 폴더 구조 (제안)
```
prototype/
├─ shared/        규칙 엔진(순수 TS): 전투 계산, 성장 곡선, 환생, 조합 판정, 모집 확률, 데이터 검사
├─ server/        HTTP API + DB. shared를 불러 판정하고 저장
├─ web/           웹 화면(시제품). API만 부름
├─ data/          60종 카탈로그, 기술, 조합식, 스토리, 정책(시험값/승인 표시)
├─ assets/        실제로 쓰는 그림·소리만(압축본)
├─ tools/         데이터 검사, 시험 서버, 화면 캡처 검토
├─ docs/          설계·기능 목록·API 명세
└─ godot/         (나중) Godot 프로젝트. 같은 API, 같은 data
```

## 기술 선택 (제안, 바꿀 수 있음)
| 부분 | 제안 | 이유 |
|---|---|---|
| 언어 | TypeScript (Node 22) | GMM110 서버·규칙이 TS라 계산식을 검증하며 옮기기 쉬움 |
| 서버 | Fastify | GMM110에서 쓰던 것과 같아 익숙함 |
| DB | SQLite + Prisma로 시작 | 서버 한 대 운영에 충분함. 필요하면 나중에 바꿈 |
| 웹 화면 | TS + DOM/CSS, Canvas는 전투 연출에만 / 묶기는 esbuild | 빠르게 고치기 쉽고 의존성이 적음. Godot의 Control 노드 배치와 사고방식이 비슷함 |
| 시험 | Vitest(규칙·API), Playwright(화면 캡처) | 계산식은 숫자로, 화면은 캡처로 확인 |

## Godot으로 옮길 때를 위한 약속
- 웹 화면 구조를 Godot 장면처럼 짠다. 화면 하나 = 장면(scene) 하나이고, API·계정 상태는 전역 모듈 하나(Godot의 autoload에 해당)가 맡는다.
- 화면끼리 직접 부르지 않고, 「장면 전환(이름, 인자)」과 「신호(signal)」로만 연결한다.
- 화면 크기는 가로 전용. 기준은 휴대폰 915×412와 큰 화면 1280×720(GMM110 검토 기준과 같음).
- API 응답은 화면에 바로 쓸 수 있는 모양으로 준다(남은 턴, 이유 문구, 사용 가능 여부). 그래서 Godot 쪽에서 규칙을 다시 계산하지 않는다.
- `docs/API.md`(2단계에서 작성)를 웹·Godot 공통 계약으로 쓴다.

## API 방향 (초안)
- 주소: `/api/v1/...`, JSON.
- 모든 쓰기 요청은 `requestId`(같은 요청을 다시 보내도 한 번만 처리)와 필요한 경우 `revision`(낡은 화면 명령 거절)을 가진다. GMM110에서 검증된 방식이에요.
- 로그인: 6자리 코드, 카카오. 세션은 웹은 쿠키, 앱은 머리글 토큰.
- 묶음(GMM110 기능 기준): 계정 · 마을(home) · 보유 개체 · 도감 · 첫 갈매미 · 모집 · 조합 · 편성 · 전투 · 스토리/의뢰 · 모험 · 일반전/랭크전 · 환생 · 방범대장 · 상점/우편/일일.

## 정한 것 (사용자 결정, 2026-11-13)
1. **예전 체계는 뺀다**: 수비대 전투, 145종 카톡 챗봇, 예전 실시간 대전은 새 프로젝트에 옮기지 않는다.
2. **시제품 동안은 시험 계정만** 쓴다. 운영 계정·DB는 이어받지 않는다.
3. **시험값도 그대로 옮긴다.** 시험값 표시는 유지한다.
4. **그림은 60종과 GMM110에서 실제로 쓰인 것만** 옮긴다.
5. **기존 도메인(gmm.dpdns.org) 아래**에 띄운다. 경로와 배포 방법은 서버 단계에서 정한다.

## 비교 시험의 한계 (3단계 기록)
- 시험이 실제 차이를 잡는지 일부러 계산을 틀리게 넣어 확인했어요. 공개 시점·경험치 반올림·저항 배율·강제 교체 순서는 잡혔어요.
- 「전투 중 관측을 종 단위 지식에도 더하는 부분」(`addDefenseObservation`의 base 갱신)은 꺼도 시험이 통과했어요. 원본에서 전투 안의 공개 정보는 이번 전투 관측이 종 단위 지식을 덮어쓰기 때문에(`{...base,...local}`), 상대가 한 마리인 PvE에서는 결과에 영향이 없어요. 대전(PvP)을 옮길 때 다시 확인해요.
- 기준 결과에 없는 상황: 100턴 무승부, 모험 도망 실패(도망 판정 함수 자체는 따로 비교함), 상한 초과로 경험치가 잘리는 정산(지급 함수 자체는 따로 비교함).
